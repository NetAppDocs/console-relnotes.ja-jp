* 9.16.1P16HF1
* 9.17.1P11HF1
* 9.18.1P8HF1
* 9.19.1P3HF1

=== Workload Factory



==== Workload Factoryの管理機能強化



===== カスタムダッシュボードのデータを確認して更新します

カスタムダッシュボードの指標が最後に更新された日時を確認したり、手動で更新したりできるようになりました。「データの更新」にカーソルを合わせると、最終更新日時が表示されます。

*データの更新* を選択して、新しいスキャンを開始します。スキャンが開始されたことを示すバナーが表示され、スキャンが完了するまでボタンは無効になります。

新しいデータが利用可能になったら、通知バナーの*今すぐ読み込む*を選択してダッシュボードを更新してください。

「データの更新」と「今すぐ読み込む」の両方で、Tracker にデータ収集イベントが作成されます。

link:https://docs.netapp.com/us-en/data-services-workloads/admin/manage-custom-dashboards-fsx.html#refresh-dashboard-data["カスタムダッシュボードデータを更新する方法を確認する"]



===== カスタムダッシュボードのリージョンを指定します

カスタムダッシュボードでは、リクエストに含まれていない地域を1つ以上選択するよう求められるようになりました。ダッシュボードのデータは、選択した地域に限定されます。

link:https://docs.netapp.com/us-en/data-services-workloads/admin/create-custom-dashboard-fsx.html["カスタムダッシュボードの作成方法を学習します"]



===== FSx for ONTAP リンク作成の IAM ポリシー

リンクを作成するためのCloudFormationテンプレートとTerraformコードでは、インラインのLambda権限ではなく、IAMポリシーを使用するようになりました。

link:https://docs.netapp.com/us-en/data-services-workloads/fsx-storage/create-link.html["リンクの作成方法を学ぶ"]



===== AIエージェントの動作に関する監査と追跡

Tracker を使用して、AIエージェント設定の変更と、読み取り / 書き込みモードでの各承認リクエスト（エージェントの質問とユーザーの回答を含む）を確認できるようになりました。

Workload Factory APIを介して行われたリソースの変更は、その操作を実行するWorkload Factoryサービスがログに記録します。

link:https://docs.netapp.com/us-en/data-services-workloads/admin/learn-agent.html["エージェントのアクションの監査と追跡について学ぶ"]



==== Amazon FSx for NetApp ONTAPの機能強化



===== イニシエータグループ図の改良

「クライアントアクセス管理」ページに表示される、ブロックデバイスのイニシエータグループを示す図に、ホストに関する詳細情報が追加されました。図中のホストにカーソルを合わせると、ホスト名、インスタンスID、ワークロードタイプ、リージョン、iSCSI修飾名（IQN）などのホストの詳細が表示されます。



===== Well-Architectedの問題に対するメール機能の強化

新しいメールデザインでは、Workload Factoryが検出した構成上の問題について、より詳細な情報とコンテキストを提供します。メールには、分析されたリソースの数、警告または重大な問題があるリソースの数、およびそれらの問題の内容が記載されています。また、このメールにはFSx for ONTAPのWell-Architectedダッシュボードへのリンクも記載されているため、問題をすぐに解決できます。



===== 優れた設計のダッシュボード機能強化



====== 選択された構成チェックのサポート

選択した構成に対して手動で分析を実行することで、関心のある構成のみを分析し、待ち時間を短縮できます。



====== 優れたアーキテクチャ分析における新たな推奨事項

Workload Factory は、FSx for ONTAP ファイルシステムの適切なアーキテクチャ分析に以下の構成を含めるようになりました：

ストレージワークロードの場合：

* *ホストをフェイルオーバーノードに接続*：信頼性を確保するため、アクティブ / パッシブのFSx for ONTAPファイルシステムでホストがフェイルオーバーノードに接続されているかどうかを確認します。
* *ホストを優先ノードに接続*：ホストがパフォーマンス効率のために優先ノードを使用してブロックデバイスに接続されているかどうかを確認します。
* *ARP/AIの複数デバイス検出のギャップ*：ボリュームにブロックデバイスが1つだけ接続されている場合に、ARP/AIは完全な保護範囲を提供します。ボリュームに複数のブロックデバイスが接続されている場合、Workload Factoryはブロックデバイスを新しいボリュームに移動し、各ボリュームにブロックデバイスが1つだけ存在するようにします。
* *クローンクリーンアップ*：ストレージ使用量を最適化し、コストを削減するために削除できる、30日以上前のボリュームクローンがあるかどうかを確認します。
* *igroup OSとホストの一致*：イニシエータグループ（igroup）のオペレーティングシステムがホストのオペレーティングシステムと一致しているかどうかを確認し、I/Oやパフォーマンスの問題を防止します。


Kubernetesワークロードの場合：

* *QoS設定*：パフォーマンス効率を高めるために、Kubernetesの永続ボリュームがONTAP QoSポリシーで保護されているかどうかを確認します。
* *専用KubernetesストレージVM*：ファイルシステムがKubernetesワークロードに専用のストレージVMを使用しているかどうかを確認し、分離性を向上させ、ストレージ管理を簡素化します。
* *専用のKubernetesエクスポートポリシー*：各Kubernetes永続ボリュームに、クラスターのワーカーノードからのアクセスのみを許可する専用のエクスポートポリシーがあるかどうかを確認します。
* *Kubernetes iSCSIバックエンドの双方向CHAP*：Trident iSCSIバックエンドでセキュリティのために相互CHAP認証が有効になっているかどうかを確認します。
* *アプリケーションストレージVMでの `showmount`の無効化*：クライアントがアクセスできないエクスポートを一覧表示するのを防ぐため、アプリケーションストレージVMで `showmount`が無効になっているかどうかを確認します。


データベースワークロードの場合：

* *SAP HANAスナップショットポリシー*：アクティブなデータベースデータのストレージコストを削減し、パフォーマンスを向上させるために、SAP HANAボリュームのスナップショットポリシーが「なし」に設定されているかどうかを確認します。
* *MySQLスナップショットポリシー*：アクティブなデータベースデータのストレージコストを削減し、パフォーマンスを向上させるために、MySQLボリュームのスナップショットポリシーが「なし」に設定されているかどうかを確認します。
* *PostgreSQLスナップショットポリシー*：アクティブなデータベースデータのストレージコストを削減し、パフォーマンスを向上させるために、PostgreSQLボリュームのスナップショットポリシーが「なし」に設定されているかどうかを確認します。




====== 構成の現在の値と推奨値

適切に設計されたダッシュボードでは、最適化されていない一部の構成について、現在の値と推奨値を確認できます。これは、修正する前に推奨される値を示しています。

* コールドデータ階層化
* Snapshot ポリシー
* SSDの容量余裕




===== コスト改善



====== コスト予測と分析

コスト予測機能を使用して、FSx for ONTAPファイルシステムのコストを予測できるようになりました。これは、予算計画を立て、リソースを効果的に最適化するのに役立ちます。また、コストや利用パターンに関する分析結果を確認することで、コスト最適化の機会を特定することもできます。



====== AWS コストおよび使用状況レポート（CUR）

Workload Factoryは、お客様所有のS3バケットに配信される詳細な請求記録を提供するために、AWS Cost Explorerの代わりにAWS Cost and Usage Reports（CUR）を使用するようになりました。CURはより詳細なコスト情報を提供し、高度なFinOps、チャージバック、およびコスト配分のユースケースの基盤として機能します。



===== ストレージVM移行の改善

Workload Factoryは、ストレージVMの移行に関して、ユーザーインターフェース内でより詳細なガイダンスを提供します。これには、移行を本番環境に導入する前に、段階的な手順説明とテスト実行が含まれます。

link:fsx-storage/create-replication.html["ストレージVM移行について詳しくはこちらをご覧ください"]



===== レプリケーション遅延メール通知の改善

関連するレプリケーション遅延イベントが多数発生した場合、Workload Factoryはそれらを自動的に1つのメール通知に統合するため、通知が多すぎて混乱することはありません。



===== 自動容量管理機能の強化

Workload Factoryに容量の自動管理を依頼する前に、自動容量管理通知を有効にして機能を試用できるようになりました。ファイルシステムの容量が少なくなると、通知されます。



===== 適切に設計されたダッシュボードに含まれるデータベース構成

適切に設計されたダッシュボードには、データベース構成に関する推奨事項が含まれるようになり、ベストプラクティスに基づいて設定を評価および最適化できるようになりました。ダッシュボードに含まれる最初の設定項目は以下のとおりです：

* コールドデータ階層化
* ストレージ効率
* Snapshot ポリシー
* SSDの容量余裕
* ブロックデバイスのスペース管理
* OS タイプ
* ブロックデバイスのOSタイプをホストと一致させる
* 非アクティブなブロックデバイス（LUN）
* データファイル（.mdf）の配置
* ログファイル（.ldf）の配置
* マルチパスI/Oステータス
* マルチパスI/Oタイムアウト
* クラスタークォーラム
* コンピューティングリソースの最適化


Workload Factoryコンソールでメインメニューを選択し、次に*Well-architected*を選択してWell-architectedダッシュボードを見つけます。

image:data-services-workloads/well-architected-menu-option.png["Workload Factory コンソールの Well-architected メニューオプション"]



===== スループット決定ポイント

クライアントのスループットに関する推奨事項と、自動化の判断ポイントを確認できるようになりました。判断ポイントにカーソルを合わせると、現在のSKUと推奨SKU、または一定期間内に違反した指標（％）などの詳細情報が表示されます。



==== Google Cloud NetApp Volumesの機能強化



===== Google Cloud NetApp Volumes ストレージプールを表示

NetApp Workload Factory で Google Cloud NetApp Volumes ストレージプールを表示できるようになりました。プロジェクト、クレデンシャル、リージョンでフィルタリングし、ストレージプールの名前を選択すると、ゾーン、レプリカゾーン、スループット、説明、ラベルなど、その詳細情報が表示されます。



==== OCI NetApp ストレージサービスの強化



===== OCI NSSシステムの適切に設計された分析

NetApp Workload Factoryには、OCI NSSシステム向けの適切に設計された評価機能が含まれています。この評価では、業務効率の向上に役立つ洞察、推奨事項、および改善策を提供します。

OCI Well-Architected Frameworkの以下の柱について、構成評価が利用可能です：

* 信頼性：ファイルオブジェクト容量、スナップショットポリシー、およびSSD容量の余裕
* 運用上の卓越性：ホストから認識可能な容量レポートとボリューム容量のヘッドルーム
* コスト最適化：コールドデータ階層化、スナップショットクリーンアップ、ストレージ効率化


link:https://docs.netapp.com/us-en/data-services-workloads/oci/add-credentials-oci.html["OCI NSSシステムの適切に設計された分析"]およびlink:https://docs.netapp.com/us-en/data-services-workloads/oci/improve-configurations.html["適切に設計された構成を実装する"]の詳細をご覧ください。

=== AI Data Engine



==== AI Data Engine 1.3

AI Data Engineは、NetApp Consoleを通じて管理されるメタデータインテリジェンスサービスです。接続されたシステムをスキャンしてメタデータカタログを構築し、ストレージを最適化して大規模にデータをガバナンスするための可視性とツールを提供します。AI Data Engineは、 https://docs.netapp.com/us-en/ai-data-engine/deploy/deployment-overview.html["AIDEシングルノード展開"^]として導入することも、環境で大規模なKubernetesベースの高可用性が求められる場合はAIDEマルチノード環境として導入することもできます。

AI Data Engine 1.3は、初の一般提供（GA）リリースです。

.データを展開して接続する
https://docs.netapp.com/us-en/ai-data-engine/deploy/deployment-overview.html["環境に必要な規模でデプロイします"^]:: 単一のVMですばやく開始するにはAIDEシングルノード環境を、高可用性と大規模な拡張性を実現するには独自のKubernetesクラスタ上にAIDEマルチノード環境を選択してください。インターネットへのアクセスにプロキシが必要な環境の場合は、 https://docs.netapp.com/us-en/ai-data-engine/deploy/configure-proxy.html["AIDEのプロキシについて学ぶ"^]プロキシを使用して導入してください。
https://docs.netapp.com/us-en/ai-data-engine/data-sources/connect-data-source.html["データを対象範囲に含める"^]:: ファイル共有、データベースサーバー、StorageGRIDシステムを接続し、スキャンするデータリソースを選択します。
https://docs.netapp.com/us-en/ai-data-engine/administer/monitor-deployment-health.html["スキャンを正常に保つ"^]:: デプロイメントの状態を監視して、スキャンを妨げる可能性のある問題を特定し、それらを解決するために必要な詳細情報を収集してください。


.ストレージを最適化し、データを調査する
https://docs.netapp.com/us-en/ai-data-engine/investigate/understand-dashboard.html["ストレージ容量を回復する"^]:: 設定したしきい値に基づいて、接続されているシステム全体で、利用頻度の低いデータ、古いデータ、重複データを特定し、これらのデータが最も多く蓄積されているシステムとデータ所有者を確認します。
https://docs.netapp.com/us-en/ai-data-engine/administer/configure-settings.html["組織にとってのコールドデータと古くなったデータを定義する"^]:: 保持ポリシーに合わせて、どのデータがコールドまたは古いデータに分類されるかを決定するしきい値を設定してください。
https://docs.netapp.com/us-en/ai-data-engine/investigate/understand-dashboard.html["データに関する問い合わせ先を特定する"^]:: ダッシュボードから、どのデータ所有者が最も多くのコールドデータ、古いデータ、または重複データを保有しているかを特定します。次に、調査ビューで所有者またはグループでフィルタリングして結果を確認し、連絡すべき相手を特定します。
https://docs.netapp.com/us-en/ai-data-engine/investigate/investigate-data.html["コストとリスクを削減する"^]:: アクセス時間、更新日時、作成日時、ファイルサイズ、重複状態、その他の基準で接続されているすべてのシステムをフィルタリングし、組織のデータ管理目標に合致するファイルを見つけ出します。結果に基づいて直接操作するか、基準をポリシーとして保存します。
https://docs.netapp.com/us-en/ai-data-engine/investigate/investigate-data.html["重複データを削除する"^]:: 接続されたシステム全体で重複コピーが存在するファイルを検索します。重複属性またはファイルハッシュでフィルタリングして重複グループを確認し、重複コピーを削除します。
https://docs.netapp.com/us-en/ai-data-engine/investigate/investigate-directories.html["アクセスリスクを特定する"^]:: オープンなアクセス許可を持つディレクトリを特定し、アクセス許可の見直しを優先できるようにします。
https://docs.netapp.com/us-en/ai-data-engine/investigate/investigate-structured.html["構造化データを調査する"^]:: 接続されているデータベースサーバー全体で、サイズが大きすぎる、または使用されていないデータベーステーブルを検出します。


.データに基づいて行動し、長期的に監視する
https://docs.netapp.com/us-en/ai-data-engine/investigate/take-actions.html["保管コストを削減する"^]:: ファイルをNFSまたはSMBの宛先にコピーおよびアーカイブしたり、追跡のためにアイテムにタグを付けたり、保持要件に従ってファイルを完全に削除したりすることで、組織のデータのライフサイクルポリシーを徹底します。
https://docs.netapp.com/us-en/ai-data-engine/policies/create-policy.html["データの状態を継続的に監視する"^]:: フィルタ条件を名前付きポリシーとして保存することで、コールドファイルやサイズ超過ファイルなど、時間の経過とともに繰り返し発生するデータ状況を追跡し、影響を受けるファイル数が変化したときに通知を受け取ることができます。


.管理されたAIアクセス

==== Cloud Volumes ONTAP のホストでの Azure 暗号化

Cloud Volumes ONTAP 9.19.1 GA以降、前提条件を満たす新しいAzureシングルノードおよび高可用性（HA）デプロイメントにおいて、ホストでのAzure暗号化がデフォルトで有効になります。この機能は、データがホストに書き込まれたりホストから読み取られたりする際に、エフェメラルディスクや関連するホストレベルのキャッシュを含む、VMをホストする物理サーバ上のデータを暗号化します。

AzureにCloud Volumes ONTAPを展開する前に、環境が以下の前提条件を満たしていることを確認してください：

*  `EncryptionAtHost` 機能は、お客様のAzureサブスクリプションに登録されています。 https://learn.microsoft.com/en-us/azure/virtual-machines/linux/disks-enable-host-based-encryption-cli["Microsoft ドキュメント：ホストでの暗号化を有効にする"^]を参照してください。
* 選択したVMインスタンスタイプは、Azureリージョン内のホストでの暗号化をサポートしています。 https://learn.microsoft.com/en-us/azure/virtual-machines/linux/disks-enable-host-based-encryption-cli#finding-supported-vm-sizes["Microsoft ドキュメント：サポートされている VM サイズの検索"^]を参照してください。


以下の点に注意してください：

* 追加の設定は不要です。
* これらの前提条件が満たされていない場合、Cloud Volumes ONTAPの展開でホストでのAzure暗号化は有効になりません。
* ホスト側での暗号化はAzureにのみ適用され、AWSやGoogle Cloudには適用されません。


Microsoftのドキュメント： https://learn.microsoft.com/en-us/azure/virtual-machines/disks-enable-host-based-encryption-portal["Azureポータルを使用して、ホストでの暗号化によるエンドツーエンドの暗号化を有効にします"^]



==== AzureおよびGoogle CloudのCloud Volumes ONTAPクラスタにおけるバックエンドネットワーク暗号化

Cloud Volumes ONTAP 9.19.1以降では、AzureおよびGoogle CloudにおけるHA構成のバックエンドクラスタネットワーク暗号化がサポートされています。

クラスタネットワーク暗号化を有効にすると、クラスタのパフォーマンスに影響を与える可能性があります。この機能を有効にする前に、注意を払い、環境が追加の負荷に対応できることを確認してください。

https://docs.netapp.com/us-en/storage-management-cloud-volumes-ontap/task-enable-cluster-encryption.html["Cloud Volumes ONTAPクラスタでバックエンドネットワーク暗号化を有効にする"^]



==== Azureの定期メンテナンス中の障害を軽減する機能

定期メンテナンス中、AzureはCloud Volumes ONTAP HAペアのVMを一時的に停止する場合があります。ONTAPはこの一時停止をノード障害と解釈してストレージ処理をパートナーノードに移行し、VMの再開時に元のノードに戻す場合があります（テイクオーバーとギブバック）。このプロセスにより、ノード障害が発生していない場合でも、アクティブなクライアント接続が中断される可能性があります。

Cloud Volumes ONTAP 9.19.1以降では、オプションの設定を有効にすることで、Azureの定期メンテナンスによるフリーズ期間中もHAペアが動作を継続し、自動的にテイクオーバーとギブバックを開始しないようにすることができます。


NOTE: この機能は、Cloud Volumes ONTAP 9.19.1でパブリックプレビューとして利用できます。

https://docs.netapp.com/us-en/storage-management-cloud-volumes-ontap/task-azure-prevent-freeze.html["Cloud Volumes ONTAP HAペアのAzureメンテナンス中の中断を防止する"^]

==== コンソールエージェントを介したSIEMイベント配信

Ransomware Resilience は、NetApp Console を通じてイベントを配信する既存のオプションに加えて、Console エージェントを通じて SIEM イベントを配信する機能をサポートするようになりました。

詳細については、link:https://docs.netapp.com/us-en/data-services-ransomware-resilience/task-siem.html["SIEMシステムを構成する"^]を参照してください。

==== Hyper-V ワークロードの機能強化

Hyper-Vワークロードの保護に関する詳細は、 https://docs.netapp.com/us-en/data-services-backup-recovery/br-use-hyperv-protect-overview.html["Hyper-VワークロードをNetApp Backup and Recoveryで保護する方法について説明します"]を参照してください。



==== Kubernetes ワークロードの機能強化

今回のリリースでは、Kubernetesワークロードに以下の機能強化が導入されました。

* *Trident Protect 26.08*：このリリースには Trident Protect 26.08 が含まれます。
* *バックアップの再試行*：Kubernetes 保護ポリシーの詳細設定で、バックアップの再試行を有効にし、再試行回数と再試行間隔を設定できるようになりました。
* *部分的なバックアップの成功*：Kubernetes の保護ポリシーの詳細設定で、個々のリソースが失敗した場合でもバックアップを継続するように構成できるようになり、バックアップジョブが部分的に成功した状態として完了できるようになります。これにより、バックアップ操作中に一部のリソースが失敗した場合でも、バックアップされたリソースを復元することができます。
* *「crash consistent state（障害など予期しないシャットダウン時と同様）」の状態およびVM一貫性のバックアップ*：Backup and Recovery for NetApp Consoleサービスで、「crash consistent state（障害など予期しないシャットダウン時と同様）」の状態またはVM一貫性のバックアップやスナップショットを作成する保護ポリシーを設定できるようになりました。また、保護処理中にVMのフリーズを実行する方法をカスタマイズすることもできます。
* *ConsoleエージェントのIPアドレス変更時のKubernetesクラスターの再接続*：Backup and Recovery for NetApp Consoleサービスでは、エージェントのIPアドレスが変更された場合に、クラスターをそのConsoleエージェントに再接続できるようになりました。
* *クラスターを新しいコンソールエージェントに移行する*：NetApp Backup and Recovery コンソールサービスでは、元のエージェントが故障または削除された場合に、クラスターを新しいコンソールエージェントに移行できるようになり、アプリケーションの保護が中断なく継続されます。


Kubernetesワークロードの保護の詳細については、 https://docs.netapp.com/us-en/data-services-backup-recovery/br-use-kubernetes-protect-overview.html["NetApp Backup and Recoveryを使用したKubernetesワークロードの保護について説明します"]を参照してください。



==== Oracle Databaseワークロードの強化

今回のリリースでは、Oracle Databaseワークロードに以下の機能強化が導入されました：

* *プラガブルデータベース（PDB）の復元*：個々のプラガブルデータベース（PDB）および PDB テーブルスペースを、ポイントインタイムリカバリを含めて復元できるようになりました。
* *プラガブルデータベース（PDB）クローン*：既存のターゲットコンテナデータベース（CDB）に単一のPDBをクローンできるようになりました。また、コンテナデータベース全体をクローンする際に、PDBを除外することも可能です。


Oracle Databaseワークロードの保護の詳細については、 https://docs.netapp.com/us-en/data-services-backup-recovery/br-use-oracle-protect-overview.html["NetApp Backup and Recovery を使用した Oracle Database ワークロードの保護について学ぶ"]を参照してください。

==== ダッシュボードの改善

Disaster Recovery ダッシュボードが刷新され、Disaster Recovery 環境全体を包括的かつ一目で把握できる、より優れたユーザーエクスペリエンスが提供されるようになりました。新しいダッシュボードには以下の機能が含まれています：

* *統合されたワークロード可視化* — VMwareとKubernetesのワークロードと基盤となるインフラストラクチャの状態を、単一の画面から監視できます。
* *問題の事前発見* — ダッシュボードが環境上の問題を自動的に強調表示することで、診断の迅速化と解決までの時間の短縮が可能になります。
* *容量利用率* — 容量に関する指標がダッシュボード内に直接表示されるようになり、リソース消費の状況をより簡単に把握できるようになりました。


詳細については、link:https://docs.netapp.com/us-en/data-services-disaster-recovery/use/dashboard-view.html["ダッシュボードで NetApp Disaster Recovery プランの正常性を確認する"^]を参照してください。

レポート機能が拡張され、環境全体における Disaster Recovery アクティビティに関するより詳細なインサイトを提供できるようになりました。

* VMwareワークロード、Kubernetesワークロード、またはその両方を対象としたレポートを生成することで、レポートを対象者に合わせて柔軟にカスタマイズできます。
* 各レポートは、指定された期間の完全なアクティビティサマリーを提供し、Disaster Recovery環境におけるイベントを完全に可視化します。


詳細については、link:https://docs.netapp.com/us-en/data-services-disaster-recovery/use/reports.html["NetApp Disaster Recoveryレポートを作成する"^]を参照してください。



==== ユーザージョブのログ記録

Disaster Recovery において、ユーザーレベルのジョブログ機能により、ジョブの責任性および監査可能性が向上しました。実行されるすべてのジョブには、そのジョブを開始したユーザーが記録されるようになり、コンプライアンス遵守やトラブルシューティングのための明確な監査証跡が提供されます。Disaster Recovery によって自動的にトリガーされるジョブは「system」として識別されるため、ユーザーが開始したアクティビティとサービスが開始したアクティビティを容易に区別できます。

詳細については、link:https://docs.netapp.com/us-en/data-services-disaster-recovery/use/monitor-jobs.html["NetApp Disaster Recoveryジョブの監視"^]を参照してください。
